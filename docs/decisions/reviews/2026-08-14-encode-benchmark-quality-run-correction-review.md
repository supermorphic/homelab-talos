# Spec Review

**Spec:** /Users/ksiggins/Development/homelab-talos.fileflows-movie-encoding-strategy/docs/decisions/2026-08-14-encode-benchmark-quality-run-correction.md
**Reviewer:** Claude Opus 5, Claude Code CLI (independence from the authoring client unverified)
**Verdict:** Not ready — the capability gate's failure branch turns a known harness-side telemetry gap into a "QSV is ineligible, stop" verdict, and the `-nostdin` correction's scope leaves the savings panel with the same input-drain defect.

## Findings

### F1 — Defect
**Where:** §4 PR A ("If it fails, record QSV as ineligible and stop Task 4") with §1 (telemetry criterion) and §Context ("GPU busy evidence files were empty")
**Mechanism:** §1 makes a capability pass conditional on GPU engine telemetry being "present and increases during the encode". PR A's four bullets strengthen the proof, flip the committed evidence to `pending`, add dispatch/assigned-node refusals, and add regression tests. None of them changes where telemetry comes from; the only source in the harness is the sysfs glob `/sys/class/drm/card*/engine/*/busy` (`benchmark.sh:1128`), and `qsv_proof` records a `telemetry` suspect reason whenever the delta is not positive (`benchmark.sh:348`). PR B's bullets do not touch telemetry either, so the replacement interface named in the author's open list has no home in the rollout.
**Failure:** The capability Job runs on a node whose GPU really is encoding, reports `telemetry` as its only suspect reason, and exits nonzero. §4 offers exactly two branches, so the operator takes the failure branch: QSV is recorded as ineligible and Task 4 stops. A working platform is retired on a harness measurement gap — the platform-versus-harness conflation Goal 2 exists to prevent.
**When:** Whenever the engine `busy` files are absent, unreadable, or non-numeric inside the runtime pod — the exact condition the audit already observed on this cluster.

### F2 — Ambiguity
**Where:** §2 heading "Quality harness corrections" and §2.1 "Every FFmpeg invocation receives `-nostdin`"
**Reading 1:** The corrections are scoped to the quality harness, so `-nostdin` is added to the ffmpeg calls the quality sweep reaches. Implementation: patch the quality path; `savings_mode` keeps its current shape — a `while IFS= read -r sample` loop fed by process substitution (`benchmark.sh:1563`, closing at `:1604`) with every foreground ffmpeg (`run_qsv_encode` at `:1154`, decode at `:1251`, VMAF at `:1262`, SSIM at `:1272`) running directly in the loop body. Because the savings loop has no inner clip loop to absorb the drain, the first title's encode consumes the remaining `savingsPanel` records and the 24-title savings run encodes one title. §3's test list contains no savings-iteration assertion, so this passes CI.
**Reading 2:** `-nostdin` is applied to every ffmpeg invocation in every runtime script, including `stills.sh:120-123`, so `savings_mode`, `finalist_mode`, and `contention_mode` — which share `process_variant` and the same loop shape — are corrected at the same time, and the PR B diff and its test set are correspondingly larger.

### F3 — Defect
**Where:** §5 Runtime expectation, read against §2.4 ("Only those samples run the initial x265 sweep, extensions, and comparison output")
**Mechanism:** §5 instructs the implementation plan to "calculate a new range from all observed per-variant times and verify that the Job's 36-hour deadline remains credible before dispatch." The number of x265 encodes is not observable in advance: the bracketing loop runs once per clip for two VMAF targets (highest and lowest QSV point, `benchmark.sh:1495-1497`) and `x265_next` steps CRF by ±2 until the QSV point is bracketed or the CRF bound of 10 or 34 is reached (`benchmark.sh:250-289`), so a clip can consume up to 13 x265 points. The stopped run recorded only the four initial Goodfellas points and no extension encodes, so "all observed per-variant times" contains no sample of the quantity that dominates the total.
**Failure:** At the spec's own measured rate (4.5 h for four points ⇒ ~1.1 h per Goodfellas x265 point), Goodfellas alone reaches 3 clips × 13 points ≈ 43 h — past `activeDeadlineSeconds: 129600` (36 h, `templates/job.yaml:15`) before a single QSV encode, VMAF pass, SSIM pass, or still. The kubelet terminates the Job with `backoffLimit: 0`, and the partial run is only recoverable by an operator-directed resume whose identity check includes `node.name` (`runmeta.sh:210`), so a resume that lands on the other eligible node aborts on an identity diff.
**When:** Whenever the QSV points on the grain-heavy HDR10 sample are not bracketed by CRF 18–24 — the case the accepted extension mechanism exists for, and the expected case on grain-heavy material.

### F4 — Contradiction
**Where:** §1 (assigned-node runtime proof) and §4 PR A (capability Job disposition)
**§1 says:** "committed evidence from one node cannot make a run on another node expensive before that node proves the same capability" — capability is treated as a per-node property, which is the entire justification for repeating the proof at runtime.
**§4 says:** "If it fails, record QSV as ineligible and stop Task 4." The capability Job carries only `podAntiAffinity` against Plex and no node pin (`templates/job.yaml:34-41`), so the scheduler places it on one of the two non-Plex GPU nodes.
**Why both cannot hold:** If a pass on one node says nothing about another node, a failure on one node cannot support a cluster-wide "QSV is ineligible" verdict. §4 draws exactly the inference §1 forbids, in the opposite direction, from a single unpinned Job.

### F5 — Defect
**Where:** §2.2 ("A multi-stream fixture with a PGS subtitle proves that subtitle encoder selection cannot make a valid video decode fail") with §2.1 ("its FFmpeg substitute")
**Mechanism:** The claim rests on real ffmpeg behavior — that `-f null` output forces encoder selection for a mapped PGS stream and that mapping only `0:v:0` does not. §2.1 establishes an FFmpeg substitute as the fixture mechanism for this work, and the existing benchmark suite already stubs `ffmpeg` on `PATH` (`tests/benchmark.bats:16` and `:85`). The spec never says which of the two the §2.2 fixture runs against.
**Failure:** Implemented with a substitute, the test asserts only that the stub was written to fail on `-map 0` and succeed on `-map 0:v:0`. It encodes the author's model of ffmpeg rather than an independent oracle, so it passes whether or not the real cause was subtitle encoder selection — and a corrected run repeats the live decode failure with green CI behind it. This is the case the brief's constraint "uses an independent oracle or genuine invariant" rules out.
**When:** Whenever the PGS fixture is built in the stub style §2.1 sets as precedent and the existing suite already uses.

### F6 — Ambiguity
**Where:** §1, "encode speed is inside the accepted 1080p range"
**Reading 1:** The range already committed in the harness — `qsv_proof` treats a sub-2160p encode as plausible at speed ≥ 2.0× and ≤ 20.0× (`benchmark.sh:355`). Implementation: reuse the existing bounds; a 3× measurement on the synthetic probe passes.
**Reading 2:** The range in the accepted design, "~8–15× realtime" for 1080p (2026-08-01 §6). Implementation: compile 8.0–15.0 into the capability gate; the same 3× measurement fails, and per §4 QSV is recorded ineligible. The two readings also differ in what is being measured: the probe encodes 5 seconds of `testsrc2` from lavfi (`benchmark.sh:987-991`), where fixed hardware-init cost is a large fraction of wall time, whereas §6's figure describes sustained throughput on real 1080p content.

### F7 — Ambiguity
**Where:** §1, "Quality, savings, finalist, and contention dispatch refuse before Job creation unless committed evidence proves the stronger contract" with "The first correction changes it from `verified` to `pending`"
**Reading 1:** The gate is a status check. `dispatch.sh` reads `runtime.capabilityStatus` from the committed samples ConfigMap (`app/samples.yaml:24`) and refuses unless it holds the new strong value; the recorded rate control, telemetry, and speed numbers are documentation. Implementation: one string comparison plus a schema-version bump; an evidence block whose status is set by hand passes.
**Reading 2:** The gate re-evaluates the recorded evidence. Dispatch refuses unless the committed block records exactly `LA-ICQ`, a passed initialization, a positive GPU busy delta, and a speed inside the band — so the same predicate as `qsv_proof` exists in a second place, and the committed schema must carry the numeric measurements rather than the current booleans.
The two produce different committed artifacts and different guard strength against a stale or edited evidence block.

## Grounding

- **"The existing capability probe … only checks that an encode succeeds."** Checked `capabilities()` at `benchmark.sh:919-1011`. Confirmed: it encodes with the production QSV flags, decodes, runs a VMAF pass, and emits a JSON object of booleans (`hevcQsv`, `realQsvEncode`, `decoded`, `libvmaf4k`, `libx265`) with `status: "passed"`. It asserts nothing about selected rate control, telemetry, or speed, and it does not call `run_qsv_encode` or `qsv_proof`.
- **"Foreground FFmpeg commands inherited the clip loop's standard input."** Confirmed. `quality_mode`'s clip loop reads from process substitution (`benchmark.sh:1475`, closing `:1544`); the clip extraction at `:1477` is already protected by `</dev/null`, but `run_qsv_encode` (`:1154`), `run_x265_encode` (`:1174`), the decode check (`:1251`), VMAF (`:1262`), SSIM (`:1272`), and both ffmpeg calls in `stills.sh` (`:120-123`) are not. The same shape exists in `savings_mode` (`:1563`–`:1604`), where the drain would consume panel entries rather than clip entries.
- **"The implementation ran x265 on every encodable sample."** Confirmed at `benchmark.sh:1484-1489`; no reference marker exists in the committed samples.
- **"The measured x265 runtime … disproved the 2–3 hour estimate" and the 36-hour deadline.** Confirmed `activeDeadlineSeconds: 129600` at `templates/job.yaml:15`. The per-variant times themselves live in the failed run's `results.csv` on the share, which is outside this worktree — **UNVERIFIED**; §5's 4.5 h and 13.5 h figures are taken from the spec.
- **"All 25 QSV rows reported ICQ … every QSV proof was `suspect`" and "GPU busy evidence files were empty."** **UNVERIFIED** — the run artifacts are not in the repository. What I did verify: the only telemetry source is the sysfs glob at `benchmark.sh:1128`, its awk filter accepts `video`/`vcs`/`vecs` engine paths (so i915 names like `vcs0` would match), and an empty or non-numeric read yields `telemetry` as a suspect reason at `:348`.
- **`x265Reference` marking is expressible against committed data.** Checked the parsed samples ConfigMap: cohorts are `vc1`, `avc`, `hdr10`, `dolby-vision`; the two operator-selected grain titles are `avc-grain-memento` (cohort `avc`) and `hdr10-grain-goodfellas` (cohort `hdr10`), and `dolby-vision-sisu` carries `detectionOnly: true` with an empty `clips` object. §2.4's "exactly one AVC and one HDR10 reference, rejected on detection-only entries" is checkable offline against these fields.
- **"The accepted three 90-second clip roles."** Confirmed: all six encodable quality-panel entries define exactly `detail`, `dark`, `motion`.
- **"The previously committed capability evidence."** Confirmed at `app/samples.yaml:24` — `"capabilityStatus": "verified"` with an eleven-field `capabilityEvidence` block recording `nodeName: "nuc1"`. It is part of `samplesDigest` in the run identity (`runmeta.sh:186-215`), so flipping it changes every future run ID.
- **§1's "GPU busy percentage" as a recorded field.** `sample_drm_busy` writes nanosecond timestamps (`date '+%s%N'`, `benchmark.sh:1111`) while `busy_metrics` computes `total_delta * 100 / elapsed` (`:315`). That is a percentage only if the counter's unit is also nanoseconds; against a millisecond counter the recorded value is low by 10⁶. I verified the arithmetic; the unit of the replacement interface on this platform is **UNVERIFIED** and is one of the author's open items.
- **Whether an independent ffmpeg oracle is available offline (relevant to F5).** Confirmed that a real ffmpeg is pinned — `.mise.toml:15`, `"conda:ffmpeg" = "8.1.2"` — and that `tests/helpers/runtime-sandbox.bash` symlinks the host's resolved `ffmpeg`/`ffprobe` into a restricted PATH and fails loudly if they are missing. Also confirmed that parts of the existing suite bypass that sandbox with a PATH stub (`tests/benchmark.bats:16`, `:85`). Note the pinned binary is ffmpeg 8.1.2 while the runtime image is `linuxserver/ffmpeg@sha256:4a4ed3a9…`, so an offline oracle and the live runtime are different builds.
- **"x265 … extensions, and comparison output."** Confirmed the extension and comparison loops select rows on column 10 (`status`) equal to `passed` (`benchmark.sh:1491`, `:1501`, `:1525`), per the header at `benchmark.sh:10`. A variant that fails any validation field is therefore excluded from the curve rather than reported into it.
